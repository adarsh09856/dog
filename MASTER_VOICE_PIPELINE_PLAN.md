### Live TTS phrase-gap regression (23 October 2026)

In `SpeachesLiveTTSService`, the local aggregator previously released a first phrase after only 14 characters and a comma clause after 8. The TTS service awaits each HTTP synthesis generator before processing the next phrase, so a short first fragment creates another sequential request and an audible pause while the following chunk is synthesized. Regression evidence used a Hindi reply from recent call patterns: before the fix it dispatched `ठीक है, तो कृपया` (16 characters) and then the remaining 55 characters as separate requests. The service now waits for a complete sentence or a clause of at least 24 characters at a natural comma/semicolon boundary; it no longer emits the arbitrary 14-character phrase. The same short Hindi reply now dispatches once, and a longer reply splits at its comma. The short-reply regression failed before the change. After both TTS fixes, the combined aggregator, local-model cleanup, interruption, and playback suite passed 68 tests. This reduces request-induced gaps but may delay first audio when the model emits a long unpunctuated sentence. It is source-only and has not been deployed or checked in a real browser/telephone call; actual first-audio time remains unverified.

The same Speaches adapter previously returned silently if a successful response contained no PCM chunks. It now retries that empty-success case once and emits an explicit `ErrorFrame` if the retry is also empty; provider `ErrorFrame`s are passed through without retry. Three focused tests cover recovery, exhaustion and non-retry of real provider errors. This hardens the no-audio path but cannot establish why the live endpoint returns empty bodies without live server logs.
